## §1 — Goal and consumers (G1)

Two defects share one root: the check surface hands its consumers facts as **side effects and prose** instead of **typed inputs and outputs**.

1. **Which constraint a diagnostic is about** crosses crate boundaries only inside message text; four consumers recover it by parsing or rebuilding that text (§2.1), and the build merge loop over-matches today.
2. **What geometry a check measured** is read from Engine side tables that only other public calls fill and that the GUI reload never clears (§2.2). `Engine::check`'s verdicts depend on which calls preceded it; `cmd_check`'s two branches disagree on that sequence.

## §2 — Current state at main (measured 2026-10-13, `cef0d08edc`)

### 2.1 Constraint identity in prose
- `reify_core::Diagnostic` is `#[non_exhaustive]`, `#[derive(Debug, Clone)]`, fields `severity, message, labels, code, candidates`; no serde, no `PartialEq`. Struct literals exist only in `error` / `warning` / `info`; a `compile_fail,E0639` doctest guards non-exhaustiveness. `ConstraintNodeId { entity, index }` lives in `reify_core::identity` (`Debug, Clone, PartialEq, Eq, Hash`). Labels are `Option<String>` on `CompiledConstraint` / `ConstraintCheckEntry`, unique per entity, not per module; the `ConstraintChecker` input carries ids only and its public contract says checkers "SHOULD embed `id.to_string()`".
- `ConstraintResult` carries the id per verdict; `Engine::push_constraint_result` / `labeled_entry` flatten its messages into a bare `Vec<Diagnostic>` and the id is lost there. `labeled_diagnostics` rewrites only that result's own messages (its two `contains(&id_str)` are self-guards, not selectors).
- **Producers of the grammar** `constraint {subject} violated|indeterminate` — 7 production format strings: `SimpleConstraintChecker` (2), `dispatch_constraints`' RepresentationWithin Info (coded `ConstraintIndeterminate`) and `ConstraintUpgrade::new`'s claim (2), reify-lsp (3, incl. `constraint_violated_message`'s id fallback). The checker also emits a `ConstraintViolated`-coded "evaluated to non-boolean value". `gdt_verdict` / `gdt_unmeasured` emit the same codes with no id.
- **Consumers selecting by text — four, not the record's three:** (a) `replace_superseded_constraint_diagnostics` (`starts_with(claim)`, anchored); (b) the post-geometry merge in `Engine::build_with_geometry_output`: a retract leg and a carry-over leg, each a bare `d.message.contains(&needle)` with `needle` the label or the id; (c) reify-cli `indeterminacy_subject_in` / `is_falsified_indeterminacy` with `INDETERMINACY_PREFIX` / `INFIX` — moving to `check_verdict.rs` in S27 τ #8758 and widened by #5404's in-flight branch (`CONSTRAINT_CLAIM_PREFIX`, `VIOLATION_INFIX`, `enum ConstraintClaim`, `drop_falsified_constraint_diagnostics`: a matcher for VIOLATED claims too); (d) reify-lsp `violated_messages`, rebuilt per Violated entry and compared by full-string equality, beside the LSP's own uncoded span-aware `constraint_violated_message`.
- **The record's `[1]`/`[10]` collision is vacuous** (`]` terminates the needle). The live over-matches of (b) are an **entity-suffix collision** (`XFoo#constraint[1]` contains `Foo#constraint[1]`) and a **short label** colliding with other text. Only the CLI pins the short-label case; nothing pins the entity-suffix case.
- **A live false pass hides behind the grammar (#7990).** `reify check` on a geometric `Conforms` prints `OK Conforms#0[0]` plus `warning: Conforms INDETERMINATE: could not resolve the nominal feature geometry handle` and exits 0: the build post-geometry re-check upgrades it with the language-level predicate and `merge_post_build_verdicts` adopts the upgrade. The warning survives only because it carries no id (`main.rs::idless_indeterminate_warning_survives_an_upgrade`).
- Lossy mirrors of `Diagnostic`: `PersistedDiagnostic` (`persistent_cache/diagnostics_wire.rs`, pinned-bytes test), `DiagnosticOnDisk` (reify-shell-extract), `DiagnosticInfo`, LSP `convert_diagnostic`.
- `DiagnosticInfo` (reify-core; `DiagnosticCode`'s serde derive is feature-gated; reify-core has no runtime `serde_json`; `strum` is a dependency) has `code: Option<String>` and `has_location`; no constructor from `Diagnostic`. Production literals: `diagnostics_to_info` and the two hot-reload builders in `gui/src-tauri/src/engine.rs` (`code: None` or a free string), reify-cli `mcp_context.rs` (deleted by #6665). Free strings: `"hot-reload-error"` (2 sites) and `"unresolved-source"` (1 site, set only `if d.code.is_none()` on tessellation diagnostics positioned against an empty source — a property of the projection). No TypeScript reads either; `docs/debug-mcp-contract.md` and `gui/src/types.ts` mention them. #7757 records the same strip plus a severity-blind WARN log in the same block.
- INV-SF-6 is prose (`design-invariants.md` §INV-SF-6) about codes only; PDIAG cannot see this problem (every verdict producer is coded).

## §3 — Resolved design decisions

- **D1 — One typed subject.** `Diagnostic.constraint: Option<ConstraintSubject>`, `ConstraintSubject { id: ConstraintNodeId, label: Option<String> }`. No single-variant enum: one subject kind exists; a second kind is a later refactor (heuristic 6 over speculative generality). Matching compares `id` only; the label rides for display.
- **D2 — Attached at the flatten point, rendered in one home.** `labeled_entry` / `push_constraint_result` attach `ConstraintSubject { id: result.id, label }` to **every** message of a `ConstraintResult` that lacks one, so the invariant holds by construction for third-party and mock checkers and for builtin diagnostics produced inside one constraint's evaluation (`Rejection::into_diagnostic` outputs included). The verdict grammar's renderer lives in reify-constraints (a `verdict` module: violated / indeterminate / RepresentationWithin Info / non-boolean), used by `SimpleConstraintChecker`, `dispatch_constraints` and the GD&T passes; reify-core holds the type, not the English. `labeled_diagnostics` renders the label from the subject; its self-guards go with it. The non-boolean case gets its own code (`ConstraintNonBooleanValue`) so "violated" names one condition (INV-SF-6).
- **D3 — Supersession compares ids, for both claim kinds and both merge legs.** `ConstraintUpgrade` holds a `ConstraintNodeId`; `replace_superseded_constraint_diagnostics`, the build merge loop's retract leg and the CLI drop a diagnostic iff its code is the superseded claim's code (`ConstraintIndeterminate`, or `ConstraintViolated` for #5404's falsified-violation claim) and its subject id equals the upgraded id. The merge loop's carry-over leg carries a diagnostic iff its subject id is in the carried set; a diagnostic without a subject is never selected by id. Every claim-text constant and parser (`INDETERMINACY_*`, `CONSTRAINT_CLAIM_PREFIX`, `VIOLATION_INFIX`) is deleted. β lands after #5404 and #7990 (R4).
- **D4 — Mirrors carry the subject or prove they never see one.** `PersistedDiagnostic` and `DiagnosticOnDisk` either round-trip `ConstraintSubject` (the pinned-bytes test re-pinned deliberately) or a test shows they never carry a constraint-verdict diagnostic. `DiagnosticInfo` does not carry it (the GUI keys constraints on `ConstraintData.node_id`).
- **D5 — Measurement is a required argument (R5).** `check`, `check_snapshot`, `check_constraints_with_values`, `edit_check`, `upgrade_indeterminate_verdicts` and `check_constraints_post_geometry` take `&MeasurementContext`; no check-time pass reads `achieved_repr_tol`, `realization_handles` or `capture_repr_tol` (row C6). Every caller states its posture: tests that do not measure pass `&engine.unmeasured_context()`; tests that inject measurements use `MeasurementContext::measured_for_test` (feature `test-instrumentation`, replacing `set_achieved_repr_tol_for_test`); the measuring tests (`process_dfm_measure.rs`, RepresentationWithin bt6/bt7/c4, the inline GD&T handle-injection tests) take `measure`'s context. No convenience wrapper.
- **D6 — Posture is stated by the surface, its cause derived from capability.** `MeasurementPosture::{Measured, Unmeasured(cause)}`, causes `NoCapableKernel`, `SurfaceDoesNotMeasure`, `PendingInPass`, `Stale`. Callers never name `NoCapableKernel`: `Engine::unmeasured_context()` yields `SurfaceDoesNotMeasure` on a BRep-capable engine and `NoCapableKernel` otherwise (today's `unmeasured_reason` arm 1; `has_repr_capable_kernel` moves into this derivation). `measure` on an engine without a BRep-capable kernel yields `Unmeasured(NoCapableKernel)` (it still realizes for values when asked); a `Measured` context with no entry for a realization reproduces today's "kernel present but nothing tessellated" wording. Standalone `build` / `build_snapshot` / `realize_for_check` / `tessellate_snapshot` run their internal check with `unmeasured_context()`, preserving `reify build`'s pinned attribution and `reify eval`'s and GUI export's; only a surface nested inside `Engine::measure` uses `PendingInPass`, which emits no attribution (closes #6206). Every pinned attribution wording stays.
- **D7 — A measurement is valid for the content it measured.** Each context entry records the realization's `upstream_values_hash`; the context records the engine's identity and its kernel generation (advanced by `reset_geometry_for_reload` and every kernel reset). A check uses an entry only when the current value's hash and the kernel generation match; otherwise the entry is `Unmeasured(Stale)`, reported through the RepresentationWithin attribution's existing Info form (`ConstraintIndeterminate`, own wording; no new code, no per-edit Warning). An entry whose hash is the zero placeholder is always `Stale` — never a verdict from an unverifiable entry — and ε3 replaces the production zero placeholders so measured entries carry real hashes. `reset_geometry_for_reload` also clears `realization_handles`. #6898 γ's displayed-staleness flag reads `MeasurementContext::is_current(&engine)` instead of a second counter (amendment, §6).
- **D8 — Two producers of a measured context, both stamped.** `Engine::measure(&mut self, module, &MeasureRequest) -> Measurement { context, build: Option<BuildResult> }` runs what the request asks — realize (`build` is `Some` iff it realized), capture + `tessellate_realizations`, OpenVDB — restores `capture_repr_tol`, and returns the realization's `BuildResult` for the CLI's merge legs. `Engine::capture_measurement(&self) -> MeasurementContext` snapshots what the caller's own build and tessellate produced: a GUI session that wants DFM/GD&T handles runs `build_snapshot`, then `tessellate_snapshot` with capture on (#6898 A3: no second tessellation), then `capture_measurement`. The Engine fields stay as the surfaces' stores until S1 moves per-call outputs onto `BuildResult` / `TessellateResult`; `measure` and `capture_measurement` keep their contract across that move, and ε2 keeps the accessor name `pub fn achieved_repr_tol` when its key type changes.
- **D9 — The achieved table has a typed key.** The `surface_subtree` callback receives a typed (occurrence, realization index) key instead of `entity_path: String`; resolution is a direct lookup on the value's `realization_ref` or a typed occurrence-equality scan, preserving C-BOUND-1/2 with no string grammar; `realization_belongs_to` is deleted. ε2 chooses between `RealizationNodeId` (entity = occurrence path, as the string key encodes today) and a dedicated occurrence key, and records why in the type's rustdoc.
- **D10 — One CheckEnginePlan, derived once.** `CheckEnginePlan::for_module(&CompiledModule) -> CheckEnginePlan { kernel: KernelNeed, measure: Option<MeasureRequest> }` in reify-eval `check_plan.rs`. `measure` is `Some` iff the module carries geometry, a geometric Conforms, a RepresentationWithin bound or a DFM rule; `realize` iff it carries geometry, a Conforms or a DFM rule; `capture_repr_tol` iff a RepresentationWithin bound; `openvdb` iff a thickness DFM rule (the conjunction ported as is). The `module_has_*` detectors move to reify-eval `module_capabilities.rs` (public; `cmd_build` and `cmd_eval` keep using `module_has_geometry` / `module_has_isosurface`). Both `cmd_check` branches build one engine and, when `measure` is `Some`, one `Measurement` from the plan; otherwise they pass `unmeasured_context()` (the light arm). The plan takes the module the front end yields, so it layers under `compile_program` without waiting on #5516. Other subcommands' engine choices are S1's `EngineConfig`.
- **D10b — `--purpose` measures (R3).** The measure passes take the active constraint set as an argument: `check` passes the template walk's set, the purpose path the graph walk's set including purpose-injected constraints. `Engine::check_with_values_measured(module, values, active, &ctx)` runs `dispatch_constraints` + GD&T + DFM + `run_gdt_check_passes` over it. The purpose branch activates its purposes first and measures after (so the measured hashes are those of the bound values), then calls it. Structural-query expansion stays the template walk's (#6904 item 3 reconciles the two enumerations). #6904's `activate_purpose_session` extends this shape. ζ2 inventories the 59 `--purpose` assertions and re-baselines those that pinned an unmeasured verdict.
